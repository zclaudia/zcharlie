# 选股—观察—持仓漏斗：系统设计

状态：Proposed（候选方案，待评审后替代 [`delivery-roadmap.md`](delivery-roadmap.md) 中的 V1/V2，
并同步修订 [`engineering-baseline.md`](engineering-baseline.md)，见第 14 节）

日期：2026-10-06（第 2 版，按产品愿景修订）

适用范围：`zcharlie` 的下一阶段产品形态。本文不以现有实现为出发点，
只在第 12 节说明与现有代码的映射关系。

## 0. 摘要

产品愿景（单一用户，个人投资）：

1. 从目标池（如沪深 300）按模板规则自动筛出候选股票。
2. 跟踪候选，观察它们是否进入可操作区间（可买、不再候选等）。
3. 记录持仓，当持仓进入加仓、减仓或复核区间时给出提示。
4. 以上规则可定义、可更新；有变化或需要人介入时主动通知。

系统设计为**一条漏斗的三段**：目标池 → 候选 → 观察 → 持仓。三段共用一套时点数据、
一个因子库、一个确定性规则引擎，只是规则集和频率不同。

"操作建议"在本设计中有严格定义：**建议 = 用户批准过的规则被触发**。
系统报告"你的规则 X 在 600519 上触发了，条件是……"，不产生独立于规则的意见。
规则由三层制定：项目提供模板，LLM 为每只股票起草实例并由用户批准，回测与决策日志校准模板。
LLM 起草规则与抽取事实，永不执行规则、永不打分、永不做操作决定。

## 1. 目标与非目标

### 目标

1. 目标池每周按模板规则产出候选，每只附可追溯到快照字段的触发理由。
2. 候选与持仓每日对照各自的区间规则，进入区间时产生带规则引用的事件。
3. 持仓可录入、可快照、可回放；仓位类因子（权重、成本盈亏）进入规则引擎。
4. 规则是版本化数据：模板、实例、参数变更均可追溯，可在历史快照上回测。
5. 通知分"信息"与"需要介入"两级，经真实渠道推送，不只落盘。
6. 每次晋级、移出、加减仓记录（用户操作）进入不可变决策日志，用于复盘与校准。

### 非目标

- 系统不自行产生操作意见。不存在"系统认为应该买"这种输出，只有"你的规则触发了"。
- 不自动执行任何交易，不连接券商，不生成委托。
- 不输出目标价、收益预测或情景收益数字。
- LLM 不生成或修正数值、因子分、排名、候选名单，不做加减仓判断。
- 不做盘中信号、高频扫描、多用户、订阅、社交或公开荐股。

## 2. 核心模型：一条漏斗

```text
目标池（指数成分，如沪深 300；可配置多个）
   │  ① 模板筛选：因子库 × 筛选规则，周频，确定性
   ▼
候选（数十只，每只附触发理由与起草的区间规则）
   │  ② 区间检测：候选规则（可买区 / 不再候选），日频
   │  ③ 人工晋级 ← 必须批准该股的区间规则
   ▼
观察池
   │  ④ 区间检测：观察规则（进入可操作区 / 证伪复核），日频
   │  ⑤ 用户录入建仓 ← 系统不执行
   ▼
持仓
   │  ⑥ 区间检测：持仓规则（加仓区 / 减仓区 / 清仓复核），日频
   │  ⑦ 用户录入加减仓 / 清仓
   ▼
归档 + 复盘
   │
   ▼
⑧ 校准：规则触发 → 用户实际操作 → 远期结果 → 修订模板默认参数（升版本）
```

### 标的状态机

| 状态 | 进入方式 | 退出方式 | 由谁驱动 |
|---|---|---|---|
| `universe` | 属于目标池成分 | 调出成分（保留历史） | 系统 |
| `candidate` | 本周筛选命中，或用户手动提名 | 晋级、忽略或过期（默认 14 天） | 系统提议，用户处理 |
| `watching` | 用户晋级，并批准该股区间规则 | 用户移出（必填理由） | 用户 |
| `holding` | 用户录入建仓 | 用户录入清仓 | 用户 |
| `archived` | 从 watching/holding 移出 | 重新提名 | 用户 |

每次状态迁移写入决策日志。用户可以绕过筛选直接提名或直接录入持仓，
来源记为 `manual`，同样必须批准区间规则。

## 3. 设计原则

1. **一套因子库，三套规则集。** 因子定义只有一份；筛选规则、候选/观察规则、持仓规则
   都只能引用因子库中的因子（含仓位类因子）。标的沿漏斗下移时口径连续。
2. **建议即规则触发。** 所有"可操作"提示都引用一条用户批准过的规则及其版本；
   没有规则就没有提示。
3. **系统提议，人决定，人执行。** 规则由 LLM 起草、用户批准；状态迁移和仓位变化只能由用户录入。
4. **规则是数据。** 声明式、可渲染、可回测、可版本对比；不是 Python 代码。
5. **时点纪律。** 任何计算只用 `as_of` 当时可得的数据；快照不可变；目标池成分也按时点记录。
6. **变化驱动。** 默认视图是"上次以来发生了什么"：新候选、新触发、规则待批准。
7. **未校准即标注。** 在回测校准之前，模板默认参数是假设；触发事件必须标注"基于未校准模板"。
8. **LLM 只起草、只抽取。** LLM 可以起草规则实例、抽取披露中的事实；不执行规则、不打分、不做操作判断。

### 模块职责

| 模块 | 输入 | 输出 | 确定性 | 频率 |
|---|---|---|---|---|
| Provider adapter | 供应商响应 | canonical 记录 | 是 | 每日 |
| PIT Snapshot Store | canonical 记录、持仓录入 | 不可变快照 | 是 | 每日 / 事件 |
| Factor Library | 快照 | 因子值（含缺失 / 不适用标记） | 是 | 按需 |
| Rule Engine · 筛选 | 因子值 + 筛选规则 | 候选 + 理由 | 是 | 周 |
| Rule Engine · 区间检测 | 因子值 + 该股区间规则 | 区间事件 + 理由 | 是 | 日 |
| 规则起草 Agent | 股票数据 + 模板 + 用户历史偏好 | 规则实例草稿 + 起草理由 | 否（LLM） | 候选产生时 / 用户请求时 |
| Rule Store | 草稿、审批、修改 | 版本化规则 | — | 事件驱动 |
| Notifier | 候选、区间事件、待批准规则 | 推送（两级） | 是 | 事件驱动 |
| Decision Journal | 用户操作 | 不可变日志 | — | 事件驱动 |
| Calibration | 历史快照 + 区间事件 + 日志 | 回测报告、模板修订建议 | 是 | 月 / 季 |
| 证据抽取 Agent [P4] | 披露原文 | 候选事实 | 否（LLM） | 观察池内按需 |

## 5. 规则制定：三层模型

这是本设计的核心机制，回答"规则由谁制定、怎么制定"。

| 层 | 制定者 | 内容 | 变更方式 |
|---|---|---|---|
| **模板层** | 项目（开发阶段由用户与开发者共同定义） | 策略原型 + 默认参数 + 适用行业 + 三类区间的默认条件 | 升级模板版本，附回测对比 |
| **实例层** | LLM 起草，用户批准 | 某只股票采用哪个模板、参数如何覆盖、证伪条件 | 用户批准 / 修改 / 驳回；每次修改升实例版本 |
| **校准层** | 回测 + 决策日志 | 对模板默认参数的修订建议 | 进入模板层的版本升级流程 |

### 5.1 模板层

- 首批模板来自现有评分内核的五个策略原型：红利蓝筹、质量成长、稳健质量成长、周期反转、高成长风险投资。
- 每个模板声明：适用行业、筛选条件（进入候选）、候选区间（可买区 / 不再候选）、
  持仓区间（加仓区 / 减仓区 / 清仓复核）、默认参数、参数的允许范围。
- 模板参数在校准前是假设；模板带 `calibration_status: uncalibrated | backtested | validated`。

### 5.2 实例层：LLM 起草，用户批准

- 触发时机：股票进入候选时自动起草；用户提名或录入持仓时起草；用户随时可要求重新起草。
- 起草输入：该股因子值与历史分位、所属行业、可用模板、用户过去批准/驳回的规则（偏好信号）。
- 起草输出：一份规则实例草稿 + 逐条起草理由（为何选此模板、为何调整某参数）。
- 约束：草稿必须通过 schema 校验——只能引用因子库中存在的因子、参数在模板允许范围内、
  不得引入自由文本条件。校验失败的草稿不进入待批准队列。
- 用户操作：批准、改参数后批准、驳回（附理由）。驳回理由进入决策日志，作为后续起草的偏好信号。
- 批准后规则变为 `active`，LLM 不再参与该规则的执行。

### 5.3 校准层

- 回测对象：模板默认参数在历史快照上的触发事件与远期结果（第 9 节）。
- 决策日志信号：某类触发用户总是忽略 → 阈值可能过松；用户经常手动改同一参数 → 默认值应修订。
- 输出是**模板版本升级提案**，仍需用户批准；不自动修改任何 active 规则。

### 5.4 规则表达

规则是声明式数据，LLM 可起草、UI 可渲染、回测可重放、版本可 diff。示意：

```yaml
rule_id: 600519/quality_growth/v3
template: quality_growth@v2
scope: holding                  # screen | candidate | holding
status: active                  # draft | active | retired
approved_by: user
approved_at: 2026-10-06
calibration_status: uncalibrated
zones:
  add:                          # 加仓区间
    all:
      - { factor: pe_percentile_5y, op: "<=", value: 0.25 }
      - { factor: position_weight, op: "<", value: 0.08 }
  trim:                         # 减仓区间
    any:
      - { factor: gain_vs_cost, op: ">=", value: 0.40 }
      - { factor: position_weight, op: ">", value: 0.15 }
  exit_review:                  # 清仓复核：只提示复核，不建议清仓
    any:
      - { factor: gross_margin, op: "<", value: 0.88 }   # 证伪条件
      - { factor: roe, op: "<", value: 0.20 }
notify: { add: info, trim: info, exit_review: action_required }
```

约束：

- 条件只能引用因子库中的因子；仓位类因子（`position_weight`、`gain_vs_cost`、`holding_days` 等）
  由持仓快照计算，同样在因子库中定义。
- 区间名是固定枚举：候选用 `buy_zone` / `drop`，持仓用 `add` / `trim` / `exit_review`。
  不存在 `sell` 区间；证伪条件触发的是复核。
- `op` 限于比较与区间，不支持任意表达式。

### 5.5 规则生命周期

`draft` → `active` → `retired`。每次修改产生新版本，旧版本保留。区间事件永远引用触发时的规则版本，
历史回看显示的是"当时的规则"。模板升级不会自动改写已 active 的实例，只生成"建议更新"提示。

## 6. 核心数据模型（草案）

| 实体 | 关键字段 | 说明 |
|---|---|---|
| `snapshot` | `as_of`, `symbol`, `kind`, `provider`, `payload`, `schema_version`, `captured_at` | 不可变；含 `universe_membership` 与 `holding` 两类快照 |
| `factor_value` | `as_of`, `symbol`, `factor`, `value`, `quality`, `factor_version` | 可由快照完全重算；含仓位类因子 |
| `rule_template` | `id`, `version`, `applicable_industries`, `screen`, `zones`, `param_ranges`, `calibration_status`, `backtest_report` | 模板层 |
| `rule_instance` | `id`, `symbol`, `scope`, `template_ref`, `version`, `status`, `definition`, `drafted_by`, `draft_rationale`, `approved_by`, `approved_at` | 实例层 |
| `screen_result` | `as_of`, `rule_ref`, `symbol`, `reasons[]` | 周筛选结果 |
| `zone_event` | `as_of`, `symbol`, `rule_ref`(含版本), `zone`, `conditions_met[]`, `calibration_status`, `notified_at` | 区间事件；可复现 |
| `candidate` | `symbol`, `opened_at`, `expires_at`, `sources[]`, `draft_rule_ref`, `status` | |
| `holding` | `symbol`, `as_of`, `shares`, `cost_basis`, `source`(manual/import) | 持仓快照，用户录入 |
| `reason` | `rule_ref`, `factor`, `op`, `threshold`, `actual`, `snapshot_ref` | 所有理由同构，可点击溯源 |
| `decision` | `symbol`, `kind`(promote/dismiss/open/add/trim/close/approve_rule/reject_rule), `reason_text`, `rule_ref?`, `context_snapshot_ref`, `at` | 不可变 |
| `evidence` [P4] | `symbol`, `claim`, `source_ref`, `extracted_by`, `confirmed_by`, `confirmed_at` | 未确认不入账 |

关键约束：`reason` 与 `zone_event` 必须引用快照与规则版本；`decision` 记录当时的上下文快照；
`holding` 的每次变动都是新快照，不覆盖。

## 7. 选股端

### 7.1 目标池

- 目标池 = 一个或多个指数成分（沪深 300 起步；可加中证 500、行业指数）。
- 成分按时点记录：回测时使用当时的成分，避免幸存者偏差。成分与行业分类来自 baostock，按周快照（见 15.1）。
- 数据层按数百至一千只的规模设计，不按全市场设计。

### 7.2 模板筛选（周频）

- 每个模板的 `screen` 条件在目标池上运行，命中即成为候选，理由为命中的全部条件。
- 行业不适用的因子记为 `not_applicable`，不视为缺失。
- 候选产生时同步触发规则起草（5.2），用户在待办中看到"新候选 + 草拟规则"。
- 目标规模：每周数十只新候选；过多说明模板太松。

### 7.3 候选区间（日频）

候选阶段的规则只有两个区间：`buy_zone`（进入可操作区，提示晋级）与 `drop`（不再候选，如估值分位回升、财报转差）。
候选过期（默认 14 天）或触发 `drop` 时自动归档并记录。

## 8. 观察与持仓端

- **晋级即批准规则**：晋级操作要求批准该股的观察/持仓规则实例（可一键采用草稿）。
- **建仓由用户录入**：`buy_zone` 触发只是提示；用户录入建仓后标的进入 `holding`，
  持仓规则开始生效。
- **持仓区间（日频）**：`add` / `trim` / `exit_review` 三类；`exit_review` 由证伪条件驱动，只要求复核。
- **变化跟踪**：沿用"只有有意义的变化才通知"，阈值按指标单独定义。
- **复盘**：清仓或移出时自动生成复盘页：当初批准的规则、期间触发的事件、用户的实际操作、期间表现。
- **证据账本 [P4]**：公告与财报由 LLM 抽取候选事实，用户确认后入账；可作为 `exit_review` 复核时的参考，
  不参与规则计算。

## 9. 通知

| 级别 | 触发 | 渠道 |
|---|---|---|
| `info` | 新候选、`buy_zone`、`add`、`trim`、规则草稿待批准、周报 | 推送 + 站内 |
| `action_required` | `exit_review`、`drop`（持仓股）、数据异常（快照缺失、供应商冲突）、模板升级建议 | 推送（高优先）+ 站内置顶 |

- 至少一个真实推送渠道（企业微信 / Telegram / 邮件 任一），落盘 Markdown 只作为审计副本。
- 同一规则同一区间在连续触发时只通知一次（进入时），离开区间再通知一次。
- 每条通知附规则引用、触发条件实际值、`calibration_status`。

## 10. 评估与校准

| 层级 | 指标 | 频率 | 用途 |
|---|---|---|---|
| 漏斗 | 候选 → 晋级转化率（按模板拆分） | 周 | 哪些模板产出对用户有用 |
| 规则 | 区间事件 → 用户实际操作的跟随率（按区间、按模板） | 月 | 规则是否被信任；总被忽略的阈值需修订 |
| 信号 | 候选分桶、各区间事件的远期 1/3/6 月收益分布 vs 目标池基准 | 季 | 模板是否有信号 |
| 数据 | 快照完整率、缺失率、延迟 | 日 | 数据层健康 |

主指标是跟随率与转化率（衡量对用户是否有用）；收益分布只做季度校验（衡量规则是否有信号）。
模板变更流程：提案 → 历史快照回测 → 新旧对比报告 → 升级模板版本 → 用户批准 → 对 active 实例发出"建议更新"。

## 11. LLM 边界

| 场景 | 是否使用 LLM | 说明 |
|---|---|---|
| 筛选、区间检测、排序 | 否 | 必须可复现、可回测 |
| 规则实例起草 | 是 | 核心场景；输出必须过 schema 校验，经用户批准才生效 |
| 起草理由、驳回后的重新起草 | 是 | 使用用户历史偏好作为输入 |
| 区间事件的自然语言摘要 | 可选 | 只复述触发条件，不增加信息 |
| 披露 → 候选事实 [P4] | 是 | 附原文定位，经人工确认 |
| 复盘摘要 | 是 | 只基于决策日志、区间事件与已确认证据 |
| 数值、分数、排名、加减仓判断 | 永不 | — |

## 12. 分阶段路线

### P1 · 目标池、模板筛选与候选

- 目标池成分按时点归档；成分股每日快照（行情、估值、最近一期财报）从第一天开始积累。
- 因子库 v1：质量、估值（含历史分位）、成长、负债、波动；行业适用性声明。
- 模板层 v1：由现有五个策略原型改写，含筛选条件与区间默认参数（标注 uncalibrated）。
- 规则引擎 · 筛选：周频候选 + 结构化理由 + 溯源。
- 规则起草 Agent + schema 校验 + 批准/驳回流程。
- 候选队列、晋级/忽略/过期、决策日志。
- 观察端沿用 MVP 能力，改为读取同一因子库。

退出条件：快照连续积累 ≥ 8 周且完整率达标；每周稳定产出候选；每条理由可回溯到快照字段；
每只候选都有通过校验的规则草稿；因子定义只有一份。

### P2 · 操作区间、持仓与通知

- 规则引擎 · 区间检测：候选区间（`buy_zone` / `drop`）与持仓区间（`add` / `trim` / `exit_review`），日频。
- 持仓录入（手工 / 文件导入）、持仓快照、仓位类因子。
- 通知两级 + 至少一个推送渠道 + 去重策略。
- 复盘页（清仓 / 移出时生成）。

退出条件：同一快照对的区间事件可复现；每只持仓都有 active 规则；
推送渠道连续 4 周稳定；每条通知可回溯到规则版本与触发值。

### P3 · 回测与校准

- 基于积累快照与时点成分的回测框架：候选分桶、各区间事件的远期收益分布。
- 跟随率 / 转化率面板。
- 模板版本升级流程、对比报告模板、"建议更新实例"机制。
- 模板 `calibration_status` 升级为 backtested / validated。

退出条件：每次模板变更附回测报告；至少一个模板达到 backtested；
对无信号的模板或区间有明确记录与处理（收紧或停用）。

### P4 · 披露与证据（可选）

- 公告 / 财报接入；证据抽取 Agent；人工确认入账。
- 证据与 `exit_review` 复核页关联；复盘引用证据。
- 行业相对强弱与主题层，作为筛选的补充维度。

退出条件：至少一类披露完成"抽取 → 确认 → 入账 → 在复核页可见"全链路。

## 14. 对工程基线的修订

本设计与 [`engineering-baseline.md`](engineering-baseline.md) 有两处明确冲突，采纳本设计时须同步修订，
不允许实现悄悄越过：

| 基线原文 | 修订为 |
|---|---|
| 第 1 节非目标："根据用户资产给出买卖、仓位或收益承诺" | "系统不自行产生买卖或仓位意见，不承诺收益；只报告用户批准的规则在其持仓或候选上的触发。" |
| 第 3 节："工作流标签只描述研究优先级，不能使用交易指令语言" | "区间事件使用固定枚举（buy_zone / drop / add / trim / exit_review），每个事件必须引用用户批准的规则版本；不存在 sell 区间，证伪触发复核而非清仓建议。" |

保持不变的红线：不自动执行、不连接券商、LLM 不出数字与操作判断、历史结果不静默重算。

## 15. 外部依赖与开放问题

### 15.1 数据源调研结论（2026-10-06）

**iFinD（经 ifind-proxy / agent_gw）** 共开放 9 个 API：`ifind_get_price`、`ifind_get_stock_realtime_price`、
`ifind_get_stock_info`、`ifind_get_holder_info`、`ifind_get_stock_announcement`、
`ifind_get_financial_statements`、`ifind_get_stock_financial_index`、`ifind_get_stock_business_segmentation`、
`ifind_get_forecast`。

| 设计需要 | iFinD | 说明 |
|---|---|---|
| 指数成分 / 历史成分 | 无 | 数据源描述提到"智能选股"，但未开放对应 API |
| 指数行情（基准、相对强弱） | 有 | `ifind_get_price` 支持指数代码，如 `000300.SH` |
| 季报 | 有 | 报告期支持 0331 / 0630 / 0930 / 1231 |
| ≥ 5 年价格历史 | 分段可得 | 单次最大 3 年区间，需分两段请求 |
| 公告 [P4] | 有 | 标题、时间、PDF 链接，仅 A 股 |
| 盈利预测 | 有 | 只返回当日预测，无历史时点版本 |
| 标准行业分类 | 无直接字段 | 只有主营业务、可比公司 |

所有 iFinD API 单次最多 3 只标的；ifind-proxy 默认限流 60 次/分钟，Kimi 网关上游配额未知。
沪深 300 每日增量约 100～200 次调用（2～4 分钟）；首次回补 5 年价格与 20 个季度两类财务指标约
4000 次调用（约 1 小时），作为一次性任务可行。

**baostock（参考数据源，已实测）**：免费、无需 token，用于指数成分与行业分类。

| 能力 | 实测结果 |
|---|---|
| 沪深 300 / 上证 50 / 中证 500 成分 | 可用，按日期查询；2005 年之前为空（指数尚未发布） |
| 历史成分时点精度 | 成分快照按周发布（`updateDate` 为周一）；能看到 6 月、12 月定期调整及临时调整（如 2025-04、2025-10 各 1 只）；生效日期精度约 ±1 周 |
| 行业分类 | 证监会行业分类（84 个大类，如 `C15酒、饮料和精制茶制造业`），可按日期查询历史；沪深 300 成分全部有行业 |
| 性能 | 单次成分查询 0.1～7 秒；全市场行业分类一次约 66 秒 |
| 代码格式 | `sh.600000`，需映射为 `600000.SH` |

已知限制与处理：

- **查询未来日期不报错**，返回最新快照（实测 2027-01-01 返回 `updateDate=2026-10-05`）。
  采集时一律以返回的 `updateDate` 作为生效日期，并拒绝 `updateDate` 晚于采集日的数据。
- 只覆盖三个指数；扩展到其他指数时再评估 Tushare Pro。
- 无成分权重；本设计不依赖权重。
- 证监会分类比申万粗；如模板需要更细的行业口径，再评估替换。

架构处理：baostock 作为独立的参考数据 provider，只负责成分与行业；采集结果按 `updateDate`
写入 PIT Snapshot Store（`universe_membership`、`industry_classification` 两类快照）。运行时与回测只读快照，
外部源不可用只影响更新，不影响已有数据。成分每周同步，行业每月同步；成分发生变化时推送 `info` 通知。

### 15.2 开放问题

1. **估值历史分位**：需要 ≥ 5 年估值历史。行情可从 iFinD 分段回补；历史 EPS / BPS 需逐个报告期回补，
   财务重述导致回补数据非时点，需单独标注。
2. **持仓录入方式**：手工表单起步；券商导出文件格式各异，导入格式需另行约定。
3. **推送渠道**：企业微信 / Telegram / 邮件 选一；内网部署时的出网策略。
4. **规则起草的偏好信号**：用户驳回理由如何结构化，才能有效反馈到下一次起草。
5. **Kimi 网关上游配额**：批量采集前需确认，必要时在 ifind-proxy 增加按批次的节流与重试。
6. **ifind-proxy 临时文件泄漏**：每次调用以 `NamedTemporaryFile(delete=False)` 创建文件且从不删除，
   批量采集前需修复。
7. **候选过期时长、通知去重窗口**：使用中调整。

## 16. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 未校准模板的触发被当作有效建议 | 用户据此操作 | 事件与通知强制显示 `uncalibrated`；P3 不可无限后推 |
| LLM 起草的规则引用不存在的因子或越界参数 | 规则不可回测 | schema 校验前置；校验失败不进待批准队列 |
| 规则过拟合（回测好看、实际无用） | 校准误导 | 主指标用跟随率与转化率；模板变更附样本外对比 |
| 规则太多、审批成为负担 | 草稿堆积 | 一键采用模板默认；只对候选与持仓起草，不对目标池全量起草 |
| 时点纪律被破坏（成分、财务重述） | 回测失真 | 成分与快照不可变；回补数据单独标注；CI 检查未来数据泄漏 |
| "建议 = 规则触发"的定义在实现中被稀释 | 系统开始替用户决策 | 代码评审以第 14 节为准；`zone_event` 必须有 `rule_ref`，无规则引用的事件视为缺陷 |

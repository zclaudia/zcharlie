## 0. 术语

- 四池命名统一为：**目标池 → 候选池 → 观察池 → 持仓池**。
- "观察标的" = 观察池内的一个条目（条目级称呼，如"移除观察标的"）。
- 观察池的既有内部命名不变：API 路径 `/watchlist`、既有数据表、代码符号仍叫 watchlist；新增契约见下文。
- 持仓池 = funnel 的 `holding` 状态 + investor-agent A1b"实际持仓账本"的用户录入前端。
- **账本快照**：某账户事实事件累计到指定 `ledger_revision` 后的不可变状态；现有 `PortfolioSnapshot` 保留其历史身份与冻结价格。
- **估值快照**：绑定账本快照、估值日期、价格引用和计算口径的不可变派生结果；规划新增 `PortfolioValuation`，同一账本版本可有多个估值结果。

## 1. 主题一：观察池的规则收口（手动添加怎么办）

### 1.1 现状

- **晋级路径**（已完整实现）：批准该股 candidate 级规则 → 写入观察池 → iFinD 核对 → 单股研究入队（`candidates/promote.py`）。
- **手动添加路径**：直接创建观察条目（代码 + 行业 + 报告年度），**没有规则、没有起草**，只是收藏语义。
- 规则 scope 枚举目前只有 `candidate` / `holding`（`rules/schema.py`）；funnel 第 2 节的 `watching` 状态在规则模型里没有自己的 scope。
- 后果：同一页面混着两种语义的条目——晋级来的有 active 规则承诺，手动加来的没有任何规则；手动条目永远不会产生 `buy_zone` / `drop` 信号。

### 1.2 候选方案

| 方案 | 做法 | 评价 |
|---|---|---|
| A. 强审批 | 手动添加必须先批准规则才能入池 | 摩擦大，把随手动作变成重流程，不推荐 |
| B. 逃生舱 | 保持现状，手动条目标"无规则"，不参与区间检测 | 语义缺口永久化，观察池长期一半条目没有规则 |
| **C. 自动起草 + 标注（推荐）** | 手动添加后，在模板已确定时自动入队规则起草；复用 `rule_draft` 的起草与校验能力，新增观察来源、任务身份和结果关联。条目照常研究、刷新；卡片区分起草中、待批准、失败和驳回。无 active 规则且驳回后标“无规则（已驳回）”，理由进决策日志 | 不增加入池摩擦；批准/驳回/改参数复用规则服务，观察条目不依赖候选晋级 |

推荐 C，理由：手动添加是高频、低成本的随手动作，不能让它变重（A 的问题）；但缺口必须可见，否则观察池的"规则承诺"定位立不住（B 的问题）。C 让"无规则"从默认状态变成一眼可见的待办状态。

### 1.3 连带决定点

1. **起草模板谁选**：手动添加时没有筛选命中，无法自动确定模板。选项：用户在表单里必选模板（与候选提名一致）／可选 + LLM 按行业与策略匹配推荐默认值／完全由 LLM 选。倾向"可选 + LLM 推荐默认值"，提交前可改。
2. **观察条目的规则 scope**：倾向**不新增 scope**——观察池条目沿用 `candidate` scope 的 `buy_zone` / `drop` 区间（两段语义本就一致：可研究 / 不再候选），晋级批准的那条规则继续生效；新增 `watching` scope 只是把同一语义拆成两份，收益低。
3. **无规则状态是否允许长期存在**：驳回后允许"纯观察"（不参与规则、只做研究跟踪），还是驳回即必须重新起草直到批准？倾向前者，但驳回理由必须填（已有流程），并让重新起草的入口一直可见。
4. **移除观察池补理由**：funnel 第 2 节规定移出"必填理由"并记决策日志；当前 UI 移除无理由输入。小成本，建议本次一并补上。

### 1.4 依赖提示

规则收口落地后，规则要"兑现"还需要 **P2 的日频区间检测**（`ZoneEvent`：`buy_zone` / `drop` 每日对照因子值产生事件）。
收口先行（数据与流程），区间检测另行排期。**2026-10-11 第三轮已实现**（WP8，见第 9 节）：批准的规则每日对照
候选因子（持仓规则对照当日估值派生的仓位因子）产生事件，事件引用触发时的规则版本；"区间检测未启用"的标注
已全部移除。在检测落地前，卡片上的"区间检测未启用"标注是如实说明；落地后该说明被区间状态行取代。

### 1.5 手动观察条目的起草与审批契约（review 问题 3）

现有起草任务用 `candidate_id + template版本` 生成幂等键，无候选时 `candidate_id = 0`，结果回调也跳过 0；现有批准入口位于候选晋级流程。不能直接将手动观察条目套入这条路径。

- **来源与请求身份**：扩展任务契约，显式记录 `origin_kind`（candidate/watchlist）、`origin_id`、canonical `listing_id`、`scope`、`draft_request_id`（UUID）和精确模板版本；不得用共同的 0 代替所有观察条目。新观察任务的幂等键使用 `rule_draft:watchlist:{origin_id}:{draft_request_id}`，限制在队列的 128 字符上限内，并绑定完整请求体。候选旧任务身份保持兼容。
- **重复提交与重新起草**：同一次添加的网络重试复用同一请求 UUID、模板版本与输入；不同股票有不同来源身份。用户明确“重新起草”才创建新请求 UUID，并冻结当次 `as_of`、模板版本和偏好输入；worker 重试复用原请求，不产生新起草意图。驳回后不自动反复起草。
- **模板未确定**：用户可选模板；LLM 推荐失败或无适用模板时，观察条目仍可保存，标“待选择模板”，提供选模板后起草入口；不向需要精确模板版本的 `rule_draft` 提交空模板。提交前的推荐可由用户修改。
- **添加与入队一致性**：模板已确定且需新起草时，观察条目、当前请求关联及队列任务在同一事务提交；模板未确定时明确保存 `needs_template`。不得出现添加成功、任务未持久化却显示“起草中”的状态；重复添加保持当前任务关联。
- **规则归属**：观察条目关联请求、任务与草稿引用；规则仍按 `listing_id + scope` 共享。同股已有 active candidate 规则时直接展示它，重复添加不自动替换。候选与观察页对同一规则展示同一版本；批准或驳回不会凭空创建候选记录或再次晋级。
- **状态分开记录**：`active_rule_ref` 与 `draft_state` 分开；后者至少包含 `needs_template / queued / drafting / ready / failed / rejected / none`。只有 `ready` 显示“规则待批准”，失败显示原因和重试入口。更新草稿起草失败或被驳回时，原 active 规则继续生效；没有 active 规则时才显示“无规则”。
- **过期任务隔离**：同一 `listing_id + scope` 的当前起草请求须由共享版本检查保护。新请求替代旧请求后，旧 worker 的写入与回调只能保留审计结果，不能退休新草稿、改写当前关联或重新激活已移除条目；检查必须覆盖草稿入库与结果关联的同一事务，不能只在回调末尾检查。移除后重新添加必须取得新的请求身份。
- **独立审批**：新增观察页的规则批准入口，复用 `RuleStore` 的版本、参数范围与生命周期校验；事务内验证标的、scope、当前草稿和用户已看到的 active 版本，批准新规则、退休旧 active 并写决策日志。驳回只退休目标草稿并记录必填理由；改参数产生新草稿版本并更新关联。状态冲突时刷新给用户重新审阅，不静默批准另一版本。
- **存量处理**：已有手动条目先关联该股有效规则或当前草稿；无规则条目标记待起草。在模板确定后按迁移请求身份一次性入队，可重跑且不重复创建任务。不能把历史条目全部标成“待批准”掩盖实际缺少草稿的状态。

## 2. 主题二：持仓池的持仓快照模型

### 2.1 现状与既有资产

- 尚无独立的持仓池列表与成本/盈亏视图；WIP 已有组合账本及 Agent 页录入 UI（见 [`ag24-portfolio-acceptance.md`](ag24-portfolio-acceptance.md)）。模型已有 `PortfolioAccount`（CAS head）、`PortfolioEvent`（append-only，含幂等键、批量导入 `batch_id/row_id`、冲销 `reverses_id`）、`PortfolioSnapshot`（按 revision 不可变）；事实类型已有 `opening_balance / trade / cash_transfer / dividend / reconciliation / corporate_action / reversal`（`storage/models/portfolio.py`、`portfolio/contracts.py`）。
- 现有 `Holding` 只记录数量，`SnapshotHolding` 记录数量与冻结估值，没有成本与建仓日期；账本快照目前只在追加事实时生成。成本投影、持有天数与每日估值必须新增，不能视为既有能力。
- A1b 组合计划服务（`portfolio/plans.py`）消费同一账本做约束校验与仓位数值计算。
- 红线（AG24 / A1b）：只有用户确认的已发生事实改变账本，包括余额、交易、资金流、公司行动与纠错；Agent 意见与用户“决定”都不生成持仓变动。写入口继承现有账户权限、`portfolio_ledger_enabled` 开关和事实确认要求；新页面不绕过 A1b 的产品开放条件。

### 2.2 模型原则（与既有资产对齐）

1. **真相 = 用户确认的事实账本**：首条事件必须是 `opening_balance`。当前持仓与现金由有效余额边界及边界后的交易、资金流、公司行动派生；不是所有录入都写成 `trade`。
2. **加减仓 = 新交易事件**；**清仓 = 卖出使数量归零**；**录错 = 冲销原事件并按需追加替代事实**。不删除或覆盖原事件与旧快照；纠错事务见 2.8。
3. **事实版本与估值版本分开**：事实变化推进账户 CAS revision 并生成不可变 `PortfolioSnapshot`；行情更新只生成绑定该账本版本的 `PortfolioValuation`，不追加虚假交易或推进事实版本。
4. **因子具有明确来源**：`position_weight`、`gain_vs_cost`、`holding_days` 由账本状态、估值日期与精确行情引用计算；结果包含计算版本、可用性和原因。规则与 Agent 使用同一组事实/估值引用。
5. **表单与文件导入共用服务端契约**：均写确认事实，使用账户 CAS、请求幂等键与导入 `batch_id/row_id`。浏览器不计算成本、现金或仓位。

### 2.3 录入表单（持仓池页，新页面）

- **账户与事实确认**：先选择/建立账户，填写资产范围、完整/部分覆盖；发生时间包含日期、时间与可见时区（默认北京时间），同时记录来源和“已发生”确认。不同账户不隐式合并现金与仓位。
- **迁入初始持仓**：默认“确认当前余额”模式，代码搜索后填写数量、可空的剩余平均取得成本、可空的本轮建仓日期，以及同一时点的现金；写 `opening_balance`，不伪造买入。另提供“从成交明细重建”模式，先确认真实历史起点，再导入交易及必要资金流。两种模式的边界规则见 2.6。
- **后续交易**：方向（买入/卖出）、发生时间、股数、实际价格、实际费用。费用可留空但标“未知”；显式 0 表示用户确认无费用。支持历史补录和原子纠错，卖出校验按发生时间回放，见 2.8。
- **现金与对账**：现金余额可空，空表示未知；后续实际转入转出走 `cash_transfer`，余额重确认走 `reconciliation` 并填写差异解释。现金字段不直接覆盖当前快照，也不把未录现金当 0。仓位的完整可用条件见 2.9。

### 2.4 展示与历史

- 持仓池列表：每只标的显示当前股数、剩余平均取得成本、最近有效收盘价与日期、浮动盈亏、持有天数、最后一次事实变动时间及估值更新时间；“现价”不得把日频收盘价表现为实时价格。未知、过期或冲突指标显示具体原因。
- 变动驱动：昨天以来有加减仓/清仓的排前面；历史补录与纠错单独标记录入时间和实际发生时间，不能表现为今天真实交易。
- 单只标的：事实时间线（含余额边界、冲销、替代事实与原因）、账本版本历史与估值历史；区分浮动盈亏、已实现盈亏与分红，不将只有期初余额的账户展示成完整历史收益曲线。
- **与观察池的关系**：建仓不要求先在观察池（funnel 第 2 节允许绕过筛选直接录入持仓，来源 `manual`）；同一标的可同时在观察池与持仓池，单股详情页汇聚两个状态（盈利事件通知已有"观察池 / 持仓"合并标签的先例）；清仓后进入持仓池归档区 + 复盘页，是否继续留在观察池由用户决定。
- 复盘页（清仓/移出时）：当初批准的规则、期间触发的事件、交易流水、期间表现——funnel 第 8 节既有设计，持仓流水是它的数据基础。

### 2.5 与 investor-agent A1b 的对接

持仓池录入复用 A1b“录入实际持仓与现金”的账户、事实服务和恢复协议；组合计划服务的约束校验、仓位数值计算消费同一账本。现有 Agent 页的录入与独立持仓页共用服务，不另建一份持仓真相。

新增估值后，组合计算、发布、状态检查与用户显式绑定的上下文须同时携带 `snapshot_ref + valuation_ref`：前者验证事实版本，后者冻结价格基础、时间与计算版本。事实改变要求重新计算；行情变化保留旧计划及其引用，按价格时效与重新研究要求标记受限，不静默替换价格或自动调用模型。旧计划继续读取原冻结快照及原计算契约，不改写历史结果；新契约与旧契约需明确版本区分。不能只刷新持仓页价格而让新 Agent 计算继续消费旧价格。

建议顺序：账户与期初余额扩展 → 成本投影与回放校验/纠错 → 录入与导入 → 每日估值及 A1b 引用适配 → 列表与历史展示，再接现金用途（purposes）与计划建议 UI。公司行动的数量、成本与现金口径见 2.7。

### 2.6 期初余额与历史明细边界（review 问题 1）

- **确认当前余额**：账户首次以 `opening_balance` 确认时点 T 的全部已知持仓、现金及覆盖范围。扩展余额中每只标的的可选成本与本轮建仓日期，并记录来源和口径；这些是用户确认的余额属性，不代表 T 发生过交易，也不扣现金。一个账户最多一个有效期初余额；已有账户补充或更正当前余额走对账或纠错。
- **从成交明细重建**：用户选择真实历史起点 T0，确认当时余额（只有用户确认空仓且现金确知时才写零数量/该现金余额）；导入 T0 之后的真实成交、费用、转账、分红和公司行动。缺少起点现金或部分事实时保留未知，不能为使计算通过而补虚构现金、交易或零费用。
- **不重复累计**：沿用余额契约 `prior_history = included_in_confirmed_balance`。排序按 `(occurred_at, recorded_revision)`；有效余额边界之前的事实只作审计历史，保留在 `excluded_prior_event_ids`，不再次改变数量、现金或成本。同一时刻后录入的事实会应用，导入预览必须提示用户核对边界，不能仅以日期猜包含关系。
- **混合输入**：已有 T 时点确认余额后补录 T 之前明细，只增加审计历史，不自动改期初成本/建仓日期；若要用于重建，须明确纠正余额边界并预览整个后续账本。数量相符不代表成本可自动确认；成本或建仓日期补充须由用户确认并生成新事实版本。
- **对账语义**：`reconciliation` 仍是同一资产范围内的余额确认，表单提供该范围全部已知持仓，不将一次单股编辑误写成“其他持仓全部归零”。数量或成本有差异时记录解释；不凭差额生成猜测交易。

### 2.7 成本、盈亏与持有天数口径（review 问题 4）

以下是本稿建议的统一计算口径，需扩展余额事实与账本快照字段，并以 `cost_method_version` 标识；金额和数量均用服务端 Decimal 计算，历史快照不可变。

| 指标/事实 | 处理方案 |
|---|---|
| 期初成本 | 数量 q、确认平均取得成本 c，剩余总成本 C = q × c。表单明确该成本含取得费用，不扣已实现收益或分红；已经包含的费用不再加一次。券商若使用“收益抵扣成本”等其他口径，保留来源值与说明，标准成本标未知，等待确认转换；不直接用于 `gain_vs_cost`。成本可空，数量与市值仍可确知。 |
| 买入 | q' = q + 买入数量；C' = C + 成交金额 + 已知买入费用，平均成本 C'/q'。原成本或买入费用未知时，该持仓标准成本继续未知，直至用户确认余额成本或纠正源事实。 |
| 部分卖出 | 按卖出前平均取得成本结转卖出部分的成本；剩余平均成本不变。已实现盈亏 = 卖出金额 − 卖出费用 − 结转成本；卖出费用未知只使现金及该笔已实现盈亏未知，不单独使剩余取得成本未知。 |
| 清仓/重买 | 数量归零后剩余成本归零，本轮持仓结束并归档；下一次买入开启新持仓周期，成本和建仓日从新周期计算。此前未知的历史盈亏仍保留未知。 |
| 分红 | 已确认到账的现金分红写 `dividend`，单独累计，不降低取得成本。到账金额/相关现金税费未知时保留现金限制，不用除息行情推断实际到账。 |
| 拆股/送股等 | 已确认的数量比例变更使数量乘比例、剩余总成本不变、平均成本反向调整、持仓周期不重置。其他配股、税费或未确认公司行动，沿用 `pending` 影响范围并扩展成本未知标记，待用户确认相应事实；不能只凭除权价自动调整账本。 |
| 对账 | 数量或成本改变时，由用户确认新的剩余成本；未确认则标成本未知，不能把不匹配的旧总成本机械沿用。数量和成本均未变的纯现金对账可保留成本。连续持仓周期确知未中断时保留原建仓日，否则要求确认或标未知。 |
| 浮动盈亏 | 市值 − 剩余总成本；`gain_vs_cost` = 浮动盈亏 / 剩余总成本，仅数量、成本和有效价格确定且总成本 > 0 时可用。总成本为 0 时可展示已知金额盈亏，比率标“分母为零”。不混入已实现盈亏、分红或假定卖出费用。 |
| 持有天数 | 估值日（北京时间日期）− 本轮建仓日，以自然日计，同日为 0；加仓与部分卖出不重置。期初本轮建仓日可空，确知时不得晚于余额确认日；未知时 `holding_days` 不可用，不用迁入日期或最后买入日代替。 |

账本快照新增每只持仓的剩余总成本、平均成本、本轮持仓身份/建仓日及各字段的来源、可用性与原因。估值快照计算浮动盈亏与持有天数，已实现盈亏和分红保留事件与周期引用。所有冲销/替代均回放这些状态。旧账本版本不补写成本；新版本只能由可证明的完整明细或用户确认余额取得成本。账户总收益率与完整收益曲线不在本次范围内。

### 2.8 历史补录、卖出校验与原子纠错（review 问题 5）

- **按事实时间校验**：普通交易、历史补录和导入使用同一投影逻辑，基于有效余额边界，按 `(occurred_at, recorded_revision)` 回放冲销后的有效事实。卖出检查的是该笔发生前的可确认数量，并校验受影响的后续状态；不得只用提交时的账户当前数量。已包含在余额边界中的历史明细保留审计，不再次套用到当前数量。
- **提交前预览**：服务端基于 `expected_revision` 返回受影响事件、数量/成本/现金变化及冲突位置。比如已清仓账户导入一段完整的历史买入 100 股、卖出 100 股，须整体按时间验证，不能因当前为 0 而逐行拒绝历史卖出；已有余额边界时同时说明这段历史是否仅用于审计。
- **未知数量不假装通过**：覆盖不完整、待处理公司行动或既有冲突导致当时数量未知时，显示“无法校验”，要求确认起点/对账或补齐事实。确定数量不足的普通卖出拒绝提交；不能以“历史补录”为由绕过。冲突导入停在预览，并给出具体事件及修正入口。
- **原子纠错**：新增多事件写入服务契约，以一个操作 UUID、原账户 revision 和精确请求体绑定冲销及替代事实；替代事实记录真实发生时间，冲销记录本次纠错时间、原事件 ID 和必填理由。同一数据库事务内写全部事件及其不可变版本，账户 current head 只对外暴露最终结果。提交前验证整组纠错回放后的有效事实，任一步失败则整体回滚；不能让用户先提交冲销、再补新交易而暴露负持仓状态。
- **删除错误事实**：仅冲销且最终回放有效时可以提交；若冲销买入会使后续卖出超量，则须同时纠正相关事实，或确认合法的新余额边界。既有冲突不能通过丢弃真实事件、默补买入或改成零数量消除；未解决字段保持受限。
- **并发与导入**：批次在预览基准 revision 上整体 CAS 提交，每行仍保留 `batch_id/row_id` 幂等。丢回执重试同一操作与请求体；重复请求返回原结果，不能只重放半个批次。若事实版本变化，原预览失效，要求重新预览确认；不同内容不能复用旧请求身份。

### 2.9 现金、覆盖与指标可用性（review 问题 6）

“已填现金”只是仓位可用的必要条件之一。账户资产范围与 `coverage = complete / partial` 必须显式记录；complete 是用户确认该范围内无遗漏资产，不代表所有账户或全部个人资产。

| 状态 | 展示与计算 |
|---|---|
| 费用空白 | 保存为未知，不能默认 0；明确提示该笔后现金及依赖现金的仓位受限。用户显式填写 0 才确认无费用；补确认费用通过原子纠错，现金重新确认通过对账。成本影响按 2.7 分开判断。 |
| 现金空白/未解决资金冲突 | `known_cash` 不可用；显示已知持仓市值小计及原因，不将小计称为总资产，也不计算账户仓位。 |
| partial 覆盖 | 已知资产只能显示小计；未列资产未知，即使现金已填、已列股票价格齐全，仍不计算完整 NAV 与 `position_weight`。 |
| 某只持仓数量或价格不可用 | 该股市值不可用；有非零或未知持仓缺少有效市值时，账户 NAV/仓位不可用。零持仓不要求价格。成本未知不单独阻断市值与仓位，但阻断其成本盈亏。 |
| 全部必要条件满足 | 用户确认范围完整、现金已知、所有持仓数量可确认、全部非零持仓行情满足时效要求，且不存在影响这些字段的未解决冲突时，NAV = 现金 + 持仓市值之和。NAV > 0 才计算 `position_weight` = 该股市值 / NAV；零/负 NAV 的比率不可用。 |

每个不可用指标输出结构化原因，可并列展示“费用未知”“现金未知”“资产覆盖不完整”“行情过期”“数量冲突”等。规则执行返回 unknown，Agent 约束校验保持受限；不可用不解释为 0 或“未触发”。对账可以恢复当前字段，但历史未知与差异仍保留。新增 UI 保留 AG24 的网络失败收据恢复、409 重新审阅和显式事实确认流程。

### 2.10 每日估值与不可变引用（review 问题 2）

每日估值属于本次持仓模型的基础能力，不能随 P2 区间检测延期。规划新增 `PortfolioValuation` 与独立的当前估值指针，保留既有 `PortfolioSnapshot` 的 `(account_id, revision)` 唯一约束及历史冻结价格；不在同一 revision 下反复覆盖账本快照。

- **估值身份**：记录账户、`snapshot_ref / ledger_revision`、估值日期、知识截止时间、各股 `price_ref / price_date`、算法版本、输入摘要、覆盖/时效状态，以及市值、NAV、权重、浮动盈亏和持有天数。通过独立 `valuation_ref` 引用不可变结果。
- **触发与刷新**：事实提交后为新账本版本生成估值；每个交易日收盘数据入库后，为当前版本生成当日估值。北京时间跨日或读取发现缺少当日结果时，触发幂等估值任务，即使没有新成交或报价也更新持有天数，并显式携带原报价日期；读取接口只返回已存不可变结果或“更新中”，不临时改写历史快照。周末/节假日最近应有行情日由交易日历决定，不把周五行情因周末自然日差值直接判过期。该刷新不调用 LLM。
- **价格时点纪律**：只用估值知识截止时间之前已采集、交易日期不晚于估值日的未复权有效行情；为每条价格保留来源引用。缺失价格或超过明确配置的交易日时效阈值时，完整估值与依赖指标不可用。停牌/数据延迟保留状态和报价日期；旧价格可作参考展示，不能隐藏限制当成当日价格。持有天数不依赖价格，有日期依据时仍可计算。
- **幂等与行情修订**：同一次估值任务固定账本引用、日期和知识截止时间，重试使用同一请求身份与精确输入；对相同账本版本、估值日期、输入摘要与算法版本复用已存结果。迟到或修订行情生成新输入摘要及新估值身份，旧结果与引用保留，不改写历史盈亏。
- **防止串版本**：估值计算完成后以账本 revision 检查并保护当前指针更新；若期间追加了事实，只保留该旧版本的审计结果，不能设为新版本的当前估值。行情修订并发时也不得让较旧估值覆盖较新结果。新事实已提交而估值尚未完成时，页面标“估值更新中”，不得混合新数量与旧 NAV。
- **读取与绑定**：持仓页展示当前事实版本、估值日期与价格日期；历史页按精确事实/估值引用读取。规则与新 Agent 计算共用同一估值，适配见 2.5；现有旧快照接口不能被假定为每日自动更新。

## 4. 首轮实现记录（2026-10-11，观察池规则收口 WP1）

已实现（代码 + 迁移 043 + 测试 + 浏览器实测）：

- **成本投影**（2.7）：余额可带用户确认的平均取得成本与本轮建仓日；买入把费用计入成本，部分卖出按卖出前平均成本结转、剩余平均不变并记录已实现盈亏，清仓归零并结束周期，下一次买入开新周期；分红不降成本单独入账；拆股按比例调整数量与平均成本且不重置周期；待确认公司行动标成本未知；成本未知只阻断成本类结果，不阻断市值与 NAV。
- **卖出提交校验**（2.8）：普通卖出超出"该笔发生前的可确认数量"时拒绝提交（不落库）；数量基础未知（覆盖不完整、待确认公司行动）时记录事实并显式标记无法校验，不假装通过。
- **原子纠错**（2.8）：`ApplyCorrection` 以一个操作 UUID + 预览时的账户 revision + 精确请求体绑定，一次操作可**冲销多个事实并追加替代事实**；全部事件与最终快照在同一事务写入，账户 head 只暴露最终状态；重复请求返回原结果，换内容即冲突；回放后若仍存在"确定基础被超出"则整组拒绝（要求同时纠正相关事实）。
- **每日估值**（2.10）：新表 `portfolio_valuation` + 账户 `current_valuation_id` 指针；估值身份 =（账本版本 + 估值日 + 知识截止 + 输入摘要 + 算法版本），同日同输入复用不可变行，迟到/修订行情生成新身份；知识截止默认为 min（估值日北京日终、实际当前时间），不会声明未来知识；相同已解析输入复用原行及其冻结截止时间，显式更早截止保留独立审计结果；价格时效按交易日历（未评审年份按工作日兜底）判定，过期价格不参与市值；持仓天数不依赖价格；权重与 NAV 只在覆盖完整、现金/数量/价格全部可用时给出；指针更新带 revision 守卫，账本并发前进时读取返回 409"估值更新中"。
- **API 与页面**：`GET /portfolio/valuations/current|history|{id}`、`GET /portfolio/listings|listing`、`POST /portfolio/corrections`；新页面 `/app/portfolio`（导航"持仓池"）：账户选择/新建、估值派生持仓表（数量、平均成本、最新收盘与日期、市值、浮动盈亏、持有天数、权重、未知原因）、事实录入（期初/对账、交易、资金流、分红）、事实时间线；写入仍受 `portfolio_ledger_enabled` 开关约束。
- **测试**：新增 `tests/test_portfolio_costs.py`（成本/纠错 11 例）与 `tests/test_portfolio_valuation.py`（估值 5 例）+ 迁移 043 测试；账本既有套件按新语义更新（确定基础超卖改为拒绝，其余保留）。
- **浏览器实测**：临时实例录入期初 100 股 @10 + 现金 10000、买入 10 股 @12（费用 5）、种入收盘价 13.2 后，页面显示平均成本 10.2273、市值 1452、浮盈 327（29.1%）、持有 102 天、权重 12.8%、总资产 11327，与手工核算一致。

## 9. 第三轮实现记录（2026-10-11，WP8 P2 日频区间检测）

WP8 是第二轮之后的唯一剩余工作包。迁移 head 变为 **045**，真实 dev 库未升级（仍在 021）；全部改动仍在工作树未提交。

### 9.1 数据模型与判定内核

- **`zone_event`**（迁移 045）：一次区间事件的不可变记录 —— `as_of`、`listing_id`、`scope`、`zone`、
  `transition`（`entered` / `left`）、`level`（`info` / `action_required`）、**非空**的 `rule_instance_id` +
  `rule_version` + 模板引用 + `calibration_status`、`conditions_met`（屏幕理由形状：factor / op / threshold /
  param / actual / quality / flags / snapshot_ref）、`inputs`（被引用因子的值与来源引用；持仓事件另有估值引用）、
  `input_digest`、`valuation_ids` / `ledger_revision` / `knowledge_cutoff`（持仓事件）、`notified_at`。
  唯一键 `(listing, scope, zone, rule instance, as_of, transition, input digest)`：同一（事实/价格快照对 + 规则版本）
  重跑不重复、可复现（`tests/integration/test_zone_detection.py` 断言重跑 0 新事件、改动输入产生新身份）。
  `rule_instance_id` **NOT NULL**：无规则引用的事件在存储层就不可能写入（验收"无规则引用视为缺陷"）。
  历史回看按事件里的 `rule_instance_id` 读当时的规则版本（`GET /rules/{id}` 与 `GET /portfolio/rule` 的 active/draft 块
  都只读规则槽，不改写）；模板版本同样冻结在事件里，模板升级不会改写已记录事件。
- **`zone_interval_state`**：每个 `(listing, scope, zone)` 一行，记录是否在区间内、进入日期、当前规则版本与
  最近通知时间；规则版本变化即重置区间（新承诺重新通知一次）。
- **内核**（`rules/screen.py` 的 `evaluate_zone_outcomes` 纯函数 + `rules/zone_detection.py`）：
  三值逻辑与筛选引擎一致（`missing` 不成立、`not_applicable` 跳过、全跳过则"未判定"）；未判定不写事件、
  不改区间状态，并在运行元数据里报出（§2.9：不可用不解释为 0 或"未触发"）。持仓因子 `position_weight` /
  `gain_vs_cost` / `holding_days` 由当日估值派生（跨账户合计数量/市值/成本，权重按合计市值/合计 NAV 重算，
  持有天数取最长周期；任一项未知则因子不可用并带原因），估值身份（`valuation_id`、账本版本、知识截止、价格引用）
  随事件冻结（§2.10 / §5.4）。

### 9.2 每日任务与触发

- **`zone_detection` 任务**（`rules/zone_jobs.py`，确定性、不调用 LLM、不占模型预算）：
  一次运行 = 一个 scope + 一个日期，幂等键 `zone_detection:{scope}:{as_of}:{reason}`；`reason` 让"新输入后的重跑"
  成为新运行而不破坏重复触发的幂等性。
- **触发**：`scheduler.zone_detection_cron`（默认北京时间 00:20，跨日兜底 + 启动补偿）；收盘/晚间行情入库后
  （`close_quote` / `close_quote_retry` / `market_snapshot`，与估值入队同一钩子）；估值任务成功落库后按账户入队
  （事实提交 → 估值 → 区间检测的链路，覆盖"事实提交入队"）。候选 scope 只在已评审交易日运行（非交易日无新行情，
  只会给同一批因子换日期），持仓 scope 每日运行。
- **通知**（funnel 9）：进入区间产生一次通知（`buy_zone` / `add` / `trim` = `info`，`drop` / `exit_review` =
  `action_required`）；连续触发（含当日输入修订）不再通知；离开记 `left` 事件但**不**通知；离开后再次进入再通知一次。
  事件行本身是站内通知（页面与 `GET /portfolio/rule/zone-events`），标的若有 AI 案例则同一进入事件写入既有
  `InvestorNotification` 外发通道（含规则引用、触发条件实际值、`calibration_status`）。

## 1. 架构调研结论（用例设计的依据）

| 层 | 现状 | 对测试的含义 |
| --- | --- | --- |
| 后端 | 内嵌模式完整：`WebSessionMiddleware` 接受 `X-API-Key`（网关桥 `gateway/manager.py` 对每个代理 HTTP 请求注入），渲染 `data-embedded="android"`、隐藏退出、配对行；带 key 访问 `/app/login` 302 回 `/app`；错 key 401/429 | 可经真实代理链路逐项断言 |
| 网关 | 仅 `/api/proxy/:backendId/*`（Bearer 设备凭证 → WS 流式通道），请求头白名单剥离 cookie | 代理链路即真机数据面 |
| App | **没有**打开 web UI 的入口：无自定义协议注册、`proxyUrl` 仅用于 JSON API、CSP 只允许 `ipc:` | **页面级内嵌体验本轮测不到**，属下一个工作包；HTML 内绝对资源路径（`/app/static/...`）在代理前缀下也不可解析（已知缺口，见 G2） |
| Web UI 前端 | `wireEmbeddedBack`（返回键关覆盖层）、`agent.js` 内嵌轮询属 WebView 内交互 | 依赖 App 入口，本轮只能验证其**传输契约**（任务快照 GET），不能驱动 UI |

## 3. G 组用例（内嵌模式 · 真实代理链路）

前置：P1 隔离栈就绪（网关 :3400、隔离后端 :8012 + worker、`$DEVICE_CRED` 已签发）。
执行方式：优先在被测 App 的 WebView 内经 CDP `eval` 发起**同源 fetch**（先把 WebView 导航到网关源，
若 Tauri 拦截外部导航则退化为宿主机 curl 经网关——数据面相同，报告如实标注执行方式）。

| # | 用例 | 步骤 | 预期 |
| --- | --- | --- | --- |
| G1 | 代理链路返回内嵌 HTML | `fetch('/api/proxy/<bid>/app', {headers:{Authorization:'Bearer <zgd>'}})` | 200；HTML 含 `data-embedded="android"`、无 `/app/logout`、含 `tauri.localhost/#pairing` 与 `设备与配对` |
| G2 | 代理链路静态资源 | `fetch('/api/proxy/<bid>/app/static/app.css', …)` | 200 CSS——同时记录缺口：页面 HTML 引用的绝对路径 `/app/static/...` 在代理前缀下不可解析（404），页面级加载需后续工作包 |
| G3 | 内嵌登录页跳转 | `fetch('/api/proxy/<bid>/app/login', …)`（redirect: manual） | 302，`Location: /app`（网关通道到后端桥一路成立） |
| G4 | 轮询传输契约（挂真实任务） | B3 发消息后任务运行中：`fetch('/api/proxy/<bid>/api/agent/tasks/<task_id>', …)` | 200 JSON 快照，`status` 字段随任务推进（≥2 次读取且终态 ∈ {succeeded, partial, failed}）——内嵌 AI 页的轮询路径 |
| G5 | 错误设备凭证（negative） | 同 G1，凭证改 `zgd_deliberately-wrong` | 网关 401 UNAUTHORIZED JSON（网关侧拒绝，不到后端） |

通过标准：G1/G3/G4 通过、G2 记录缺口结论、G5 拒绝路径正确。G1 失败时中止 G 组（链路前置）。
